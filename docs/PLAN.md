# U-Solve 문서 업무 해결 기획

기준: 2026-10-11, Asia/Seoul. **확정**은 프로토타입 방향과 세 사례의 시연 목표를 뜻하며, **미검증**은 실제 제품·도구 동작을 시험하지 않았다는 뜻이다. 합격 판정은 [완료 기준](ACCEPTANCE.md), 내부 입력은 [demo](demo/README.md)를 따른다.

## 목적과 범위

- 첫 사용자는 기술 이름보다 해결할 문서 업무를 아는 실무자다. U-Solve는 업무를 명세로 정리하고 공개 웹·GitHub·오픈소스와 자체 저장소의 설명·코드·워크플로에서 해법을 찾아 **회사 조건과 근거에 따라** 비교한다. 전체 웹을 미리 수집하거나 공개 레퍼런스를 기업의 첫 문의 필수 자료로 요구하지 않는다. 코멘토는 공개 정보를 한 줄 설명·기능·사용자 행동·근거 링크로 정리하는 **자료 형식 참고 사례**다.
- 판정은 `그대로 사용 가능 / 일부 단계 변경 시 가능 / 적합성 미확인·없음`을 구분한다. 입력·출력·작업 순서·계정·권한·비용과 교체할 모듈·담당자·준비물을 보여준다. 필수 조건이 충돌하면 제외하고, 알 수 없으면 개인화 추천·순위·시작 절차를 보류한다. 공개 사례도 회사 적합성 미판정으로 표시한다.
- 기존 상용 도구·공개 워크플로를 연결해 실제 결과까지 확인하도록 돕는다. 범용 문서 처리 엔진을 직접 만드는 것은 필수 범위가 아니다. 주 카테고리는 PDF, Docs·Word, Excel·스프레드시트지만 모든 형식과 업무 조합의 지원을 약속하지 않는다.
- 이번 중심은 **박찬건 방향의 실무자 문서 업무 해결**이다. 김성원 방향의 AI 소식 정리를 독립·부분 연결·통합할지는 미정이며 세 사례의 통과 조건에 넣지 않는다. 소식 안에서는 한국어 Threads **실제 자동 수집**, 원문 말투·반응 확인, 우연한 도구 발견, 중복 묶기와 저장·갱신이 후속 요구다. 샘플 데이터나 수동 URL 입력으로 자동 수집을 충족했다고 주장하지 않는다. 제작자 등록·포트폴리오·광범위한 수집, PPT·마스킹도 첫 시연 필수 범위가 아니다.

## 실무자가 요청하는 형식

첫 문의에는 아래 **세 항목만** 받는다. 기술 이름·공개 프로젝트·실제 문서·계정 정보는 이 단계에서 요구하지 않는다.

```text
[첫 문의]
해결할 업무:
현재 처리 순서: 1)  2)  3)
원하는 결과와 반드시 포함할 항목:

[후보 판단에 필요한 경우만, 시뮬레이션 전]
원본의 저장 위치·형식과 원하는 결과 형식:
회사 정책상 외부 AI 사용 가능성: 가능 / 불가 / 모름
현재 쓰는 서비스·저장 위치:
새 도구 설치·계정 연결 가능성: 가능 / 불가 / 모름
후보를 바꾸는 비용·기한 한도: 값 / 모름 / 해당 없음

[방향 승인 후 실제 시험 전]
대표 문서·양식과 성공 기준:
이번 문서를 선택한 도구·공급자에 전송할 허용: 허용 / 불허 / 모름
이번 시험의 계정 연결 허용: 허용 / 불허 / 해당 없음 / 모름
이번 시험의 유료 호출 허용: 허용 / 불허 / 해당 없음 / 모름
결과 검토자·시험 대상·잘못 반영했을 때의 복구 방법:
```

여러 문서 요약에는 **두 건 이상**의 원본·요약 범위·독자·출처 표시 기준을, 회의록에는 원문·결과 열·담당자/기한이 없을 때의 표기를, 양식 초안에는 양식 본문·근거 자료·빈칸 표기 기준을 승인 후 확인한다. 파일 첨부가 기본이고 본문 붙여넣기도 받는다. 모르는 조건은 `모름`으로 남긴다. U-Solve가 돌려줄 명세에는 업무·현재 절차, 입력·원하는 결과, 확인된 조건·미확인, 필요한 기능, 다음 단계를 분리한다. 비밀키·로그인 정보는 요청서에 적지 않는다.

## 사용자 흐름과 증거 경계

1. 첫 문의를 작업 명세로 바꾸고, 후보를 바꾸는 조건만 짧게 확인한다. 비용·설정 시간·기한이 선택을 바꾸면 첫 시험 전 한도를 묻는다. 실제 요금·시간이 확인되기 전에는 `무료`·`저비용`·기한 적합성을 단정하지 않는다.
2. 후보의 공개 설명·코드·설정 조건을 회사의 입력·출력·이용 제약과 대조한다. 문서상 지원, 코드 정적 확인, 작성자의 실행 주장, U-Solve의 실제 실행은 각각 다른 증거 상태다.
3. U-Solve 안에서 현재→제안 과정, 담당 주체, **빈 예상 결과 구조**, 가정·미확인을 `시뮬레이션`으로 보여준다. 회의록은 2D 과정도와 빈 결과 표가 첫 사례다. 복잡한 업무의 이해에 도움이 될 때 2D·3D 보기를 검토하되 근거 없는 정확한 도면·치수·실제 결과를 꾸미지 않는다. 조건이 부족해도 빈 구조의 미리보기는 제공한다.
4. 사용자가 방향을 수정·승인한 뒤 실제 문서·양식·권한을 요청한다. **설계 승인이나 사전 정책상 `가능`은 해당 문서의 전송·계정 연결·유료 호출 허용이 아니다.** 필요한 허용이 없으면 그 동작을 실행하지 않는다.
5. 허용된 기존 도구로 대표 문서 본문을 시험하고 입력·실행 기록·결과·원문 근거를 사람이 대조한다. 운영 시트·공유 문서에 쓰기 전 시험용 대상 또는 승인 대기 단계를 마련하고 검토자·복구 방법을 정한다. 입력·출력 증거가 없으면 `처리 완료`나 `AX 완료`로 표시하지 않는다.
6. 반복 적용은 별도 성장 단계다. 새 문서 재실행, 중복 방지, 사람 검토·복구를 확인한 범위에서만 반복 자동화 완료라고 표시한다.

AI 에이전트는 업무 설명을 명세로 바꾸고, 후보의 출처·조건을 대조하고, 가정이 표시된 설계 미리보기를 만들고, 실제 결과의 누락·추정을 검토하도록 돕는다. 기존 템플릿과의 차이는 **회사 조건과 템플릿의 차이, 바꿀 단계, 첫 결과의 원문 근거**를 한 흐름으로 연결하는 데 있다. 사용자 효과는 아직 가설이며 에이전트 수·모델·공급자·구현 구조는 정하지 않았다.

## 2026-10-12 22:00 시연 목표

**세 사례 모두 입력 본문을 새로 읽고 각각 결과물을 만드는 것**이 목표다. 회의록은 첫 대표 검증 순서일 뿐 다른 두 사례를 취소하지 않는다. [내부 Markdown 입력](demo/README.md)은 공개 설명의 요약과 가상 회의로 만든 시험 자료이며 실제 기업 문서가 아니다.

| 사례 | 입력 | 기대 결과 | 대표 실패 |
|---|---|---|---|
| 여러 문서 요약 보고서 | 서로 다른 공개 워크플로 설명 3개 | 문서별 공통점·차이, 출처·조건·미확인을 구분한 보고서 | 한 문서 누락, 출처 없는 기능·비용·실행 성공 단정 |
| 회의록 후속 조치 | 가상 회의록 | 결정과 할 일·담당자·기한·원문 위치를 구분한 표와 승인 전 2D 과정도 | 결정/할 일 혼합, 없는 담당자·기한 추정, 근거 없는 행 |
| 정해진 양식 초안 | 빈 평가 양식과 공개 설명 문서 | 양식 항목을 따른 근거 있는 초안, 근거 없는 칸의 `미확인` | 항목 누락, 근거 없는 비용·권한·실행 상태 기재 |

각 사례에서 **원본을 보존한 복사본의 사실 한 곳을 바꿔 다시 실행**하고 결과가 바뀌어야 한다. 세 사례의 기획·사전 판정 기준은 작성했지만 제품 코드·연결 도구·실제 입출력 기록은 없다. Markdown 본문 시연과 PDF·Docs/Word·Excel·시트 **실제 파일 연동**은 별도 판정이다. 10월 12일에 세 사례 외 추가로 증명할 파일 입출력 조합은 아직 사용자가 정하지 않았다.

## 공개 근거와 첫 후보의 한계

- 회의록→후속 조치 표를 첫 대표 업무로 고른 근거는 [Microsoft의 회의 생산성 조사](https://www.microsoft.com/en-us/worklab/work-trend-index/will-ai-fix-work), [Google Meet의 회의 메모 기능](https://workspace.google.com/solutions/ai/ai-note-taking/), [Zapier의 공개 템플릿](https://zapier.com/templates/details/extract-action-items-from-meeting-notes)처럼 업무와 기존 해법이 확인되기 때문이다. 이는 U-Solve의 연결 성공, 실제 고객 수요 규모나 비용의 증거는 아니다.
- [n8n 회의록 GitHub 저장소](https://github.com/TrentIndeed/n8n-meeting-action-items)의 JSON·예제·설정 절차는 공개돼 있다. 로컬 텍스트→Claude→Sheets 흐름이고 작성자 Windows 절대 경로의 변경, API·시트 설정이 필요하다. `agreement context` 열 안내와 실제 행 매핑이 다르며 Sheets에 바로 행을 추가한다. PDF·Docs/Word 입력, Excel 파일 출력, 사람 검토 단계는 확인되지 않았다. **코드 정적 확인만 했고 U-Solve에서 실행하지 않았다.**
- [n8n Drive 회의록 템플릿](https://n8n.io/workflows/18202-summarize-meeting-transcripts-with-google-drive-openai-gmail-and-sheets/)은 Drive 문서·TXT·VTT·SRT→AI→Gmail·Sheets 경로와 계정/API 설정을 설명한다. PDF·Word 입력과 Excel 파일 출력은 확인되지 않았고 실제 실행·요금도 미검증이다. 두 후보 모두 검토 전 운영 시트에 쓰면 안 되는 회사 조건에는 그대로 맞지 않는다. 시험용 시트·복제본 또는 승인 대기 단계를 마련·시험하기 전에는 `일부 변경 시 가능`으로도 확정하지 않는다.
- [박찬건 개인 기획 원문](https://recondite-salute-14b.notion.site/3e40a17c91ac80dfb5bee3acc7f49890?pvs=143)은 2026-10-11 확인한 방향의 출처다. 원문의 제작자 등록·자동 수집 등은 이번 확정 범위와 구분한다. `docs/reference/`는 Git 추적 밖의 과거 원자료로 남긴다.

## 남은 결정

- PDF·Docs/Word·Excel·시트 카테고리에서 추가로 **실제 파일로 증명할 대표 입력→출력 조합**과 제품 수용 범위.
- 제품 안의 도구 실행과 외부 서비스 안내 중 연결 방식, 공급자·권한·요금, 파일별 지원, 보관·전송 방식, `쉽고 저비용`의 수치 기준.
- AI 소식 안과의 관계, 제작자 흐름·반복 운영, 3D 첫 사례와 구현 방식. 내부 합성 가상 실무자 검토는 실제 고객 인터뷰·시장 검증이 아니다.

구현 요청 시 [완료 기준](ACCEPTANCE.md)으로 Seed를 만든다. 현재 문서 작업은 기획과 검증 기준까지이며 코드 구현·배포·유료 수집·Ralph 실행은 시작하지 않는다.
